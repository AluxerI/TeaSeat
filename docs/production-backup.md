# Production backup and restore

TeaSeat сохраняет два вида постоянных бизнес-данных:

- PostgreSQL: пользователи, каталог, остатки, заказы и настройки;
- `backend_public`: изображения товаров, категорий и подарочных коробок.

Redis содержит кеш, сессии и очередь, поэтому отдельно не архивируется. Каталог
импорта является временным и также не входит в резервную копию.

## Создание резервной копии

```bash
bash deploy/scripts/backup-production.sh
```

Результат сохраняется в `backups/production/<UTC timestamp>/`:

- `database.dump` — PostgreSQL custom archive;
- `public-storage.tar.gz` — публичные изображения;
- `metadata.txt` — время и Git-коммит;
- `SHA256SUMS` — контрольные суммы.

Скрипт проверяет, что PostgreSQL-архив читается. Каталог `backups/` игнорируется
Git, но это не является внешним backup: копии необходимо отправлять на другой
сервер или в объектное хранилище.

## Проверка восстановления

Восстановление полностью заменяет текущую базу и публичные изображения. Оно
требует явного подтверждения:

```bash
CONFIRM_RESTORE=RESTORE_TEASEAT bash deploy/scripts/restore-production.sh \
  backups/production/<UTC timestamp>
```

Сценарий проверяет SHA-256, останавливает gateway/backend/worker, пересоздаёт
базу, восстанавливает изображения, применяет новые миграции и запускает сервисы.

Проверку восстановления следует выполнять на отдельном тестовом Compose-проекте
или перед запуском магазина, когда потеря текущих данных допустима.

## Рекомендуемый режим на сервере

- локальный backup — ежедневно;
- отправка копии за пределы VPS — сразу после создания;
- хранение ежедневных копий — 14 дней;
- хранение ежемесячной копии — 12 месяцев;
- тестовое восстановление — минимум раз в месяц и после изменения схемы backup.

Файл `backend/.env.production` не входит в автоматический архив. Его зашифрованную
копию и `APP_KEY` необходимо хранить отдельно: без исходного `APP_KEY` невозможно
надёжно восстановить зашифрованные данные и активные cookie.
