# API менеджера: проблемы складского исполнения

## Назначение

Этот API показывает менеджеру расхождения, созданные после подтверждённой
офлайн-продажи. Он не выбирает пострадавшего покупателя и пока не изменяет
заказы. Frontend получает минимальное дело, отдельно запрашивает актуальных
кандидатов из живых онлайн-резервов и может открыть полную карточку через
`GET /api/manager/orders/{order}`.

Все маршруты требуют:

```http
Authorization: Bearer <sanctum-token>
```

Роль `manager` видит только дела активных точек из `user_warehouse`. Если связь
или сама точка отключена, доступ прекращается сразу. Роль `admin` видит все
дела, включая дела отключённых складов.

## Список

`GET /api/manager/fulfillment-issues`

Фильтры:

- `status`: `waiting`, `in_review`, `closed` или `all`;
- `warehouse_id`;
- `product_id`;
- `reason`;
- `mine=1` — только дела текущего менеджера;
- `per_page`: от 1 до 100.

Без `status` возвращаются только открытые дела `waiting` и `in_review`.
`summary` всегда содержит количество доступных менеджеру дел во всех трёх
статусах. Ожидающие дела идут первыми, внутри статуса — от старых к новым.

```json
{
  "data": [],
  "summary": {
    "waiting": 4,
    "in_review": 2,
    "closed": 9
  },
  "meta": {
    "current_page": 1,
    "last_page": 1,
    "per_page": 20,
    "total": 6
  }
}
```

## Просмотр

`GET /api/manager/fulfillment-issues/{issue}`

Ответ содержит:

- товар и рабочую точку;
- величину дефицита и резервы на момент возникновения;
- продавца, устройство и исходную офлайн-продажу;
- текущего менеджера;
- допустимые действия для авторизованного пользователя.

## Владение и статусы

```text
waiting ── take ──> in_review
in_review ── release ──> waiting
in_review ── close ──> closed
```

### Взять

`POST /api/manager/fulfillment-issues/{issue}/take`

Записывает `manager_id` и переводит дело в `in_review`. Повтор владельца
идемпотентен. Другой менеджер получает `409` и не может перехватить дело.

### Отказаться

`POST /api/manager/fulfillment-issues/{issue}/release`

Владелец возвращает дело в `waiting`, `manager_id` очищается. Администратор
может освободить дело любого менеджера. Повтор для уже ожидающего дела
идемпотентен.

### Закрыть

`POST /api/manager/fulfillment-issues/{issue}/close`

Закрыть можно только своё дело из `in_review`; администратор может закрыть
чужое. `manager_id` сохраняется. `closed` означает только прекращение текущего
разбора и не является признаком `resolved`. Из API менеджера открыть такое дело
снова нельзя.

Переходы блокируют строку `fulfillment_issues`, поэтому два одновременных
запроса не назначат двух владельцев.

## Динамические заказы-кандидаты

`GET /api/manager/fulfillment-issues/{issue}/affected-orders`

Параметр `per_page` — от 1 до 100. Backend заново выбирает строки онлайн-заказов,
которые:

- резервируют тот же `product_id` на том же `warehouse_id`;
- имеют активный складской резерв;
- ещё не списаны, не освобождены, не отменены и не удалены.

Основной клиентский заказ возвращается вместе с конкретным складским
исполнением, количеством резерва, контактом и доставкой. В `summary` есть число
кандидатов, их общий резерв и величина дефицита.

Для удобства отображения кандидаты упорядочены по количеству товара по убыванию,
затем от новых заказов к старым. Это только сортировка: backend не записывает
`affected_order_id`, не выбирает жертву и не меняет заказы.

## Граница этапа

В этот этап не входят:

- перенос даты доставки;
- заказ у поставщика;
- замена или удаление позиции;
- разделение доставки;
- отмена клиентского заказа;
- повторное открытие закрытого дела;
- архивный журнал действий.

Эти операции будут добавляться отдельными командами после согласования правил
редактирования уже оплаченных и зарезервированных заказов.
