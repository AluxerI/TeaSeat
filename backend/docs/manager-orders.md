# API менеджера: чтение и базовые команды заказа

## Назначение

Эндпоинты дают менеджеру общую картину клиентского заказа и безопасный минимум
команд, не открывая глобальный `/api/admin/orders`.

Маршруты чтения требуют Sanctum-токен и право `view manager orders`, команды —
право `manage manager orders`.

## Область доступа

- менеджер видит только заказы, которые затрагивают его активные точки из
  `user_warehouse`;
- основной заказ доступен, если его собственный `warehouse_id`,
  `destination_warehouse_id` либо хотя бы одна складская часть относится к
  назначенной точке;
- в список попадают только основные заказы, корзины и отдельные складские
  части не дублируются;
- для многоскладского заказа возвращается вся карточка, чтобы менеджер видел
  общую причину и влияние решения;
- `manager_access.assigned_fulfillment_order_ids` содержит только части,
  относящиеся к точкам текущего менеджера;
- проблема чужой складской части видна, но имеет
  `manager_accessible=false` и все её действия выключены;
- отключение склада или связи сотрудника немедленно закрывает доступ;
- администратор видит все основные заказы и все их части.

Добавить внутреннюю заметку может менеджер, которому доступна хотя бы одна
точка заказа. Подтверждение и отмена многоскладского заказа требуют активного
назначения на **все** исходные и конечные точки. Это исключает изменение чужой
складской части одним менеджером. Администратор проходит эту проверку
глобально.

Недоступный заказ возвращает `404`, чтобы не подтверждать существование чужого
заказа. Запрос фильтра по неназначенному складу возвращает `403`.

## Список заказов

`GET /api/manager/orders`

Фильтры:

- `status` — один из статусов `Order`;
- `sales_channel` — `online`, `seller` или `internal`;
- `warehouse_id` — только активная назначенная менеджеру точка;
- `has_issue=1|0` — наличие открытого `fulfillment_issue` у основного заказа
  или его складских частей;
- `date_from`, `date_to` — даты в формате `YYYY-MM-DD`;
- `search` — ID/номер `TE-*`, имя, email или телефон получателя/пользователя;
- `per_page` — от 1 до 100, по умолчанию 20.

Сортировка: сначала новые заказы. Ответ содержит компактную карточку,
`fulfillment_summary`, назначенные складские части и стандартную пагинацию.

## Карточка заказа

`GET /api/manager/orders/{order}`

Принимается ID только основного заказа. Ответ дополнительно содержит:

- контакт получателя с приоритетом снимка `contact_*` из checkout;
- оплату, итоговые суммы и сумму к получению;
- доставку, адрес, исходный и конечный склады;
- товары и подарочные наборы с сохранёнными ценами;
- все складские части, их товары и ответственных сотрудников;
- открытые и закрытые проблемы комплектации;
- складские движения основного заказа и его частей;
- историю статусов основного заказа и частей;
- клиентские и внутренние заметки;
- временные отметки исполнения.

`manager_access` содержит:

- `required_warehouse_ids` — все точки основного заказа и складских частей;
- `all_locations_assigned` — разрешена ли текущему сотруднику команда над всем
  заказом;
- `assigned_fulfillment_order_ids` — доступные ему исполнения.

Блок `actions` сообщает frontend доступность `can_add_internal_note`,
`can_confirm`, `can_cancel`, `can_reschedule` и `can_modify_items`.

## Изменение состава заказа

Состав можно менять только у неоплаченного интернет-заказа до начала сборки.
Менеджер должен быть назначен на все текущие точки; если после нового
распределения потребуется другая точка, он также должен иметь к ней доступ.

- `POST /api/manager/orders/{order}/items` — добавить товар;
- `PATCH /api/manager/orders/{order}/items/{item}` — изменить количество;
- `POST /api/manager/orders/{order}/items/{item}/replace` — заменить товар;
- `POST /api/manager/orders/{order}/items/{item}/remove` — удалить товар;
- `POST /api/manager/orders/{order}/gifts/{gift}/replace` — заменить весь набор;
- `POST /api/manager/orders/{order}/gifts/{gift}/remove` — удалить весь набор.

Каждое тело содержит обязательные UUID `operation_id` и `reason`; необязательный
`fulfillment_issue_id` связывает решение со взятым менеджером делом. Повтор с
тем же `operation_id` не применяет правку второй раз и возвращает
`already_applied=true`.

Старая строка при изменении количества сохраняет checkout-цену. Добавленная
или заменяющая позиция рассчитывается по актуальной цене каталога и текущей
автоматической акции. Остальные строки не переоцениваются. Внутренности
подарочного набора не редактируются.

В одной транзакции backend освобождает прежние резервы, меняет клиентский
документ, пересчитывает суммы, заново распределяет его по складам и создаёт
резервы. Нехватка товара откатывает все эти действия. История сохраняется в
`manager_order_adjustments` и возвращается в `manager_adjustments` карточки.
Ошибка состояния имеет код `manager_order_edit_rejected`.

## Внутренняя заметка

`POST /api/manager/orders/{order}/internal-notes`

```json
{"comment":"Клиент согласовал перенос доставки"}
```

Заметка только дописывается к `internal_notes`; существующий текст не
перезаписывается. Backend добавляет время, ID и имя менеджера. Длина комментария
— до 2000 символов.

## Подтверждение

`POST /api/manager/orders/{order}/confirm`

Тело пустое. Подтверждается только интернет-заказ в статусе `pending`, если у
основного заказа и его частей нет открытых `fulfillment_issues`. Статус
`manager_review` нельзя обойти этой общей командой: сначала проблема решается в
специализированном workflow. Основной заказ и допустимые складские части
обновляются одной транзакцией. Повтор уже подтверждённого заказа идемпотентен.

## Отмена

`POST /api/manager/orders/{order}/cancel`

```json
{"reason":"Клиент отказался от заказа"}
```

Причина обязательна, до 1000 символов. Оплаченный заказ нельзя отменить до
появления отдельного процесса возврата оплаты. Отмена освобождает только ещё не
списанные резервы через общий складской сервис и идемпотентна. Подтверждение и
отмена продаж PWA-продавца остаются в их специализированном workflow; внутренняя
заметка не меняет статус и складские данные такой продажи.

Ошибочное состояние workflow возвращает `409` и код
`manager_order_transition_rejected`; нарушение складской области — `403` с
`manager_access_denied`; недоступный заказ маскируется как `404`.

## Перенос доставки

`POST /api/manager/orders/{order}/reschedule`

```json
{
  "scheduled_delivery_date": "2026-08-19",
  "delivery_time_slot_id": 12,
  "reason": "Клиент попросил перенести доставку"
}
```

Команда доступна только для основного интернет-заказа с курьерской или
экспресс-доставкой. Backend повторно проверяет день недели и свободную
вместимость интервала под блокировкой. Причина, прежний и новый интервалы
дописываются к `internal_notes`. Повтор того же запроса идемпотентен. После
назначения курьера менеджер не переносит заказ напрямую: курьер сначала
возвращает его в очередь с причиной.
