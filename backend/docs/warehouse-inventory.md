# Складская модель TeaSeat

## Точки хранения

Склады и магазины хранятся в одной таблице `warehouses`.

- `type = warehouse` — склад;
- `type = store` — физический магазин;
- `is_active` — точка работает;
- `is_online_fulfillment_enabled` — остатки точки можно использовать для интернет-заказов.
- `is_delivery_hub` — точка, куда можно свозить части составного заказа для
  общей доставки. Для конкретного заказа сервер выбирает один активный хаб.

При распределении интернет-заказа система сначала использует точки типа `warehouse`,
а затем магазины. Отключённая для онлайн-сборки точка не участвует в каталоге,
корзине и checkout.

## Остатки

Одна запись `inventories` описывает остаток одного товара в одной точке:

- `quantity` — физическое количество;
- `reserved_online_quantity` — резерв интернет-заказов;
- `reserved_seller_quantity` — резерв заказов продавца;
- `available_quantity = max(0, quantity - reserved_online_quantity - reserved_seller_quantity)`;
- `shortage_quantity = max(0, reserved_online_quantity + reserved_seller_quantity - quantity)`.

Количество хранится в базовой единице товара: штуках или целых граммах.

## Жизненный цикл интернет-заказа

1. Checkout повторно проверяет цену и доступный остаток в транзакции.
2. Основной заказ делится на складские исполнения (`partial_orders`).
3. Для каждого исполнения увеличивается `reserved_online_quantity`.
4. Физический `quantity` на checkout не уменьшается.
5. При завершении сборки складской части физический остаток и онлайн-резерв
   уменьшаются на одно и то же количество.
6. При отмене до отгрузки уменьшается только онлайн-резерв.

Операции резерва, освобождения и списания идемпотентны. Повторный запрос не
должен применить одно складское изменение второй раз.

Упакованные части больше не входят в `inventories`. Они учитываются статусами
дочерних заказов. Части из других точек перевозятся в `destination_warehouse_id`,
подтверждаются сборщиком назначения и затем объединяются в основной заказ.

## Журнал движений

Каждое изменение баланса записывается в `inventory_movements`. Запись содержит:

- тип операции;
- изменения физического остатка и обоих резервов;
- значения до и после операции;
- заказ и сотрудника, если они есть;
- причину;
- идемпотентный ключ;
- технические метаданные.

Ручное изменение физического остатка в Filament выполняется только действием
«Корректировать остаток» и требует текстовую причину.

Интернет-заказ, созданный в Filament, проходит то же распределение и резервирование,
что и checkout. После создания резерва нельзя напрямую менять канал продажи,
адрес или позиции заказа: такие изменения должны выполняться будущими операциями
менеджера, которые одновременно обновят заказ, резерв и журнал движений.

## Каналы продаж

Поле `orders.sales_channel` принимает значения:

- `online` — интернет-магазин;
- `seller` — продажа продавцом;
- `internal` — внутреннее перемещение или заказ между точками.

Жизненный цикл `seller` реализован в API PWA: синхронизация создаёт резерв
продавца, отмена освобождает его, завершение проводит физическую продажу, а
конфликт требует отдельного подтверждения перед передачей менеджеру. Полный
контракт описан в [seller-pwa.md](seller-pwa.md).

## Данные для фронтенда

В товарных данных `total_quantity` означает доступное для интернет-магазина
количество, а не физический остаток. Детальная складская запись содержит:

- `quantity`;
- `reserved_online_quantity`;
- `reserved_seller_quantity`;
- `available_quantity`;
- `shortage_quantity`;
- `warehouse_type`;
- `is_online_fulfillment_enabled`.

Сервер остаётся источником истины: фронтенд может показывать доступность, но
checkout всегда проверяет её заново.
